# Findings (including negative and engineering results)

## F1 (Phase 3): "no forgetting" is by construction, not a result
Independent modules with frozen parameters cannot interfere. The modular system's 0.000 forgetting drop is therefore uninformative about the hypothesis; the informative comparison is the naive sequential shared-MLP baseline, which collapsed (compare_numbers 1.000 -> 0.038 after learning the next task). A joint-trained shared MLP with fewer parameters (2,932 vs 3,817 total) matched the modular accuracies on all three single tasks. **On non-compositional tasks the modular system shows no accuracy advantage over a conventional tiny network; its advantage is incremental acquisition without retraining and portable packaging.**

## F2 (Phase 4): composition works on the tested tasks, and beats end-to-end baselines where the task is compositional
With human-authored plans, independently trained modules composed reliably: measured composite accuracy matched what independent module errors predict (count_inside 0.957 measured vs 0.968 predicted; mixed 0.987 vs 0.980; A->B->A->C 0.993 vs 0.980), i.e. no sign of representation mismatch or wiring errors. End-to-end MLPs given 3,000 examples were far worse on count_inside (0.57), mixed (0.83), path_ABAC (0.86), equal on sort4 (1.00; the modular version reuses a 1,251-parameter module versus a 6,040-parameter MLP).
Caveats that limit this claim: (a) the **plans are hand-written**; whether a system can *learn or obtain* plans is untested (Phase 5-6 teacher plans, Phase 7 learned routing); (b) modules received per-module labelled supervision from the teacher, the baseline only end-to-end labels, so the comparison measures the value of decomposition plus intermediate supervision, not only architecture; (c) one baseline configuration (MLP 64x64, 3,000 examples, 150 epochs); a stronger baseline (more data/tuning) might close the gap; (d) compare_numbers has a finite 400-pair domain, which all of train/val/test cover, so composites over it test composition rather than generalization of that module.

## F3 (Phase 4): engineering bug found by the overhead benchmark
First measurement: 16-node sort plan overhead 1,443 us vs 156 us of module compute. Cause: `Registry::record_call` rewrote `registry.json` on every inference. Fix: buffer usage statistics in memory and flush on command end/drop (structural changes still persist immediately). After the fix: overhead 30-55 us for the same plan (26x lower). Trade-off: usage statistics can be lost on a crash.

## F4 (Phase 4): latency cost of modularity
Measured first with the tract backend: a monolithic end-to-end MLP took 7-9 us per task, the modular plans 66-78 us (about 9x). **Regenerated after the default backend became mlp-lite (F29): 4-7 us vs 23-28 us (4-6x)**; module compute is now only 2-4 us of a plan, so the routing/glue overhead dominates (intent routing 20-24 us per plan vs 8 us with ids). The modular design remains slower than a monolithic network wherever a monolithic network is accurate enough. Energy was not measured.

## F5 (Phase 4): scheduling
Independent branches are identified (`parallel_levels`) but executed sequentially; no parallel speedup is claimed or measured.

## F6 (Phase 5): what the detection signals do and do not catch
Ablation on 1,500 labelled cases (benchmarks/reports/phase5.*):
- **Input-novelty (training-range stats shipped in the package) removes out-of-domain fabrication**: in-scope intent with OOD inputs was answered KNOWN 100% of the time by the keyword router alone and 0% with the novelty signal.
- **Keyword routing is the weak point.** Out-of-scope tasks that share words with a capability were answered KNOWN 6.7% (generic out-of-scope set) and **35% (adversarial keyword overlap set)**, e.g. "compare prices of two shops" routed to compare_numbers. None of the numeric signals can catch these because their inputs are in-distribution. Fixing this needs a better routing signal (learned router, evaluator prediction, or teacher verification), not more thresholds. Not solved.
- **Paraphrase brittleness**: 25% of in-scope paraphrases had no keyword overlap and were sent to the teacher as unknown. In the task stream 2 of 12 related re-encounters re-triggered the teacher (and the simulator could not help), so teacher dependency on related tasks was 17%, not 0%.
- **Calibration**: temperature scaling reduced held-out ECE for all three capabilities (e.g. compare_numbers 0.058 -> 0.006), but two fits landed on the lower grid edge (T=0.05): these models are accuracy-saturated and early-stopped on accuracy, so their raw logits are under-confident. At a fixed 0.7 threshold, calibrated confidence flagged fewer boundary cases (5%) than raw confidence (15%), giving 4.9% vs 2.4% error among accepted answers at 94.7% vs 85% coverage. These are different operating points, not a clear win; a risk-coverage curve was not computed.
- Confidence gating helps only inside the learned domain (boundary points); it did nothing for unknown tasks.

## F7 (Phase 5): escalation-loop behaviour
Worked as designed: first encounters 3/3 resolved via teacher -> LearningPackage -> new module -> retry; related re-encounters mostly local; hostile or malformed teacher output (non-JSON, unknown action, bad package, reroute to nonexistent capability) activated nothing (4/4); offline unknown tasks were queued without contacting the teacher while known capabilities kept working; research/tool requests are reported as NEEDS_EXTERNAL (OpenClaw does not exist yet) instead of being faked. A bug found in my teacher simulator during the run ("send email to my colleague" classified as a memory update because of the word "my") was fixed; it also shows that nothing downstream validates the teacher's *choice of action* beyond schema checks.

## F8 (Phase 5): information classification is not solved
The rule baseline scores 20/20 on the set written alongside it (meaningless) and 5/10 on a harder set ("The sort function in this library is stable" -> CAPABILITY, "Improve at spotting fraudulent invoices" -> KNOWLEDGE, ...). It is only a placeholder gate; the schema still blocks neural training for MEMORY/KNOWLEDGE labelled packages, but a wrong label would bypass it.

## F9 (Phase 5): privacy filter limits
Regex-based redaction (emails, key=value secrets, token-like strings, paths, long numbers) plus whitelisted request fields; raw input values are never sent. Unknown secret formats or free-text personal data in an intent would pass through. The model never sees credentials only if they are not typed into the intent.

## F10 (Phase 6): spec-based teaching makes real LLM teachers feasible and safe(r), but promotion is only as good as the environment examples
A real teacher cannot reliably emit thousands of labelled vectors and its code must not be executed. The teacher now returns a declarative spec (restricted expression + domain + worked examples); a whitelist AST evaluator (no `eval`; 15/15 hostile expressions rejected in tests) labels sampled data, and promotion requires >= 0.95 on examples supplied by the *environment* (independent of the teacher). Fault matrix (benchmarks/reports/phase6.*): rule contradicting its own examples, malicious expression and a gross wrong rule were rejected 9/9; correct rules accepted 3/3. **A rule wrong on ~1% of inputs (subtle_wrong, compare_numbers) was accepted**, because it passes any tolerance-level gate. Verification cannot catch teacher errors smaller than the gate's resolution and the number of environment examples (200 here); where that matters, the gate must be tightened and the examples enlarged.
A development bug found along the way: the first version stopped after the first architecture that passed held-out accuracy and then rejected a *correct* rule because the module had reached only 0.94 on the verification examples. Verification is now inside the attempt loop (three architectures/epochs budgets) so under-training is retried instead of being reported as a bad rule.

## F11 (Phase 6): router_update removes repeat teacher calls for paraphrases, with guards
36 paraphrase tasks over 3 rounds: 9 teacher calls without persistence vs 3 with `router_update` (the 3 first encounters; 0 in rounds 2-3), all 36 answered. The update re-signs the same model bytes (verified in tests) with extra keywords, after (1) the capability passes the environment examples and (2) all previously served intents still route KNOWN to the same capability; otherwise it rolls back. Tested: an alias verified with wrong-task examples is rejected; an alias whose words collide with another capability's canonical intent is rolled back by the routing-regression check. Limits: the routing suite only contains intents served so far (collisions with unseen future intents are not detected); keyword aliases inherit the keyword router's weaknesses from F6.

## F12 (Phase 6): adaptation vs new module; forgetting is real but mild here
Extending compare_numbers to a 4x wider range: the existing module already reached 0.943 (below the 0.95 gate, so `metadata_update` was not enough); fine-tuning with replay reached 0.993 new-domain with old-domain accuracy unchanged (1.000), 0 parameters added, so it was chosen. The ablation without replay reached 0.990 new-domain but old-domain fell 1.000 -> 0.962 and would have been rejected by the regression gate. So catastrophic forgetting did not occur in this shared-parameter case, unlike the shared-MLP baseline across *different tasks* (F1); the replay buffer is a cheap, effective guard for same-task domain growth.
When the rule itself changed (point_region -> smaller circle) the labels conflict: adaptation could not satisfy both (new-domain 0.937 < 0.95, old-domain 0.992 -> 0.851), and the engine correctly fell back to a new module (+1,218 params, 0.993). Both capabilities coexist and route correctly for the tested intents (old intent -> INSIDE via point_region, new intent -> OUTSIDE via point_region__ext at the probe point). Capability count and parameters grow whenever rules conflict: module growth is not controlled yet (Phase 7 consolidation).

## F13 (Phase 6): what is still unvalidated
- No live LLM teacher was called (no credentials/egress here): runbook R1, status PENDING. The "teacher" in all experiments is the simulator (including its spec mode and fault injection), which is itself written by me and knows the ground truth; the acceptance rates above are properties of the gates, not of any real model.
- Only classification capabilities over small numeric vectors are handled by specs; no images, text or tool use.
- `adapt_existing` is evaluated on two scenarios; no claim about how often adaptation vs new modules wins in general.

## F14 (Phase 7): consolidation shrinks storage a lot, time not at all
Registry with injected sprawl (a functional duplicate, a dependency wrapper, a never-used capability, an overlapping-rule capability): 7 active capabilities / 8,851 params / 39,947 bytes -> 4 active (+3 archived, all restorable) / 3,243 params / 15,560 bytes (-63% params, -61% bytes). Contributions: duplicate merged (-1,251), two unused capabilities archived by a usage policy (-2,565), two modules distilled from 1,2xx-1,3xx to 354/420 params (accuracy -0.2 and -0.4 points on held-out sets; bytes -63%). The compare_numbers student (371 params) was **rejected by the gate** (-2.5 points: that task is close to memorisation of a 400-pair domain and needs capacity). Structured pruning and distillation ended at identical sizes with accuracy within 0.2 points of each other: no evidence to prefer either. **Per-inference latency did not change meaningfully** (measured 1-2 us before and 0-1 us after under mlp-lite, i.e. at the 1 us resolution of the measurement; 7-10 us under tract in the first run): these modules are so small that fixed per-call costs dominate, so compaction saves storage/transfer, not time. Rollback restored the original accuracy exactly (checked on an isolated copy of the runtime state). The scenario was constructed by me, so the percentages measure the tools, not how fast real registries sprawl (Phase 14).

## F15 (Phase 7): duplicate detection is sensitive to the probe distribution
Two independently trained compare modules agreed on 100% of in-distribution inputs (the packages' bundled test inputs) but only 97.9% on uniform random inputs, because neither was trained off the 20-value grid and they differ there. A 0.98 threshold on uniform probes would have missed the duplicate; on in-distribution probes it is found. Rule-conflicting modules (point_region vs the small-circle variant) scored 0.76 and were correctly *not* called duplicates. Agreement says nothing about regions neither module covers.

## F16 (Phase 7): learned routing is better at paraphrases, not clearly safer, and costs more
Hand-written evaluation intents disjoint from the training templates (27 in-scope, 24 out-of-scope, 15 adversarial; intervals are wide):
- Correct-and-KNOWN on in-scope paraphrases: keyword 0.44 [0.28-0.63] vs learned 0.81-0.89 (separated).
- Adversarial keyword-overlap tasks answered KNOWN: keyword 0.20 vs learned 0.60 (trained without hard negatives) and 0.27 (with hard negatives; indistinguishable from keyword at this n). With hard negatives the learned router *rejects* 60% of adversarial tasks (keyword: 13% rejected, 67% flagged UNCERTAIN).
- Cost: 16,708 parameters / 67 KB (more than 10x any capability module), +19 us per task (38 vs 19 us under mlp-lite; +13 us under tract), +1 MB RSS.
- **New capability after training:** the stale learned router could not route to it at all (0/4); retraining took 2.1 s and reached only 2/4 on paraphrases; the keyword router handled it immediately (3/4) from package metadata with no training.
Conclusion: under this system's growth model (capabilities arrive dynamically) the learned router as built is not a clear win; its advantage is paraphrase recall. A hybrid (keyword adaptivity + learned recall) is untested. Learned routing is not being scaled further without evidence.

## F17 (Phase 7): route optimisation works but is narrow
Common-subexpression and dead-node elimination removed half of the capability calls in two plans with injected redundancy (8->4 and 10->5), with identical outputs and ~2x lower latency. Applies only to straight-line plans with unique output slots (plans with loops/branches are left alone, enforced by a test after a crash found there). Redundancy was injected by me, so this shows the optimiser works, not that real plans are redundant.

## F18 (Phase 7): bugs and pitfalls found by checking the work
1. Admin/verification probes were incrementing usage statistics, hiding unused capabilities from the archive policy -> `--no-stats` for forced-capability runs.
2. My experiment script re-installed distilled models after a rollback test *regardless of the gate*, silently installing the rejected compare_numbers student; found by reading the output, removed; rollback is now tested on a copy.
3. The plan optimiser crashed on plans containing loops/branches (found by tests).
4. Merge-duplicate checked routing before archiving the duplicate, so both matched and every route looked ambiguous; order fixed (archive, check, restore on failure).
5. A canonical evaluation intent also appeared in the learned router's training templates (train/eval leak) and my in-script leak check was wrong; found by a test, fixed, one shared overlap check now guards both.

## F19 (Phase 8): what was actually validated about OpenClaw
Against a real install (OpenClaw 2026.6.35, Node 22.22, isolated dir, scripts disabled): the CLI flags and JSON/exit-code contract, the provider listing output, and three failure classes (no provider configured -> exit 1 "web_search is disabled or no provider is available."; same for fetch; egress blocked -> "Proxy response (403)"), all mapped correctly by the adapter and covered by a test that runs only with `OPENCLAW_BIN`. **Not validated:** any successful search/fetch (the proxy blocked the only key-less provider; no credentials), the shape of provider-specific results (parsed defensively from the source-derived envelope), `infer model run`, the agent/gateway, plugins/skills. **Live research through OpenClaw is PENDING (runbook R3).** Practical facts: the npm-latest vs `npm pack` version discrepancy is unexplained; the package is ~389 MB, so OpenClaw can only be a PC/server component.

## F20 (Phase 8): the policy boundary works as a boundary, with stated limits
15 representative requests produced the expected decisions (search allowed within limits; oversized/secret-bearing queries, off-allowlist/http/credentialed/loopback/metadata/lookalike hosts, shell, tools and unknown actions denied; file reads require approval). Per-task limits, fail-closed behaviour on engine errors (found the hard way: `aicli` required a trust store even for `policy-check`, so everything was denied until the command was made stateless), and approval binding to the exact request were tested. Limits: (a) host checks are string-based, so DNS names that resolve to private addresses and redirects are not covered by the policy (OpenClaw has its own SSRF policy, unvalidated here); (b) the approval separation is logical: any process running as the same OS user can invoke `aicli approve`, so real deployments need OS-level separation of the policy/approval files and the operator CLI; (c) the policy file is not signed; (d) secret detection is heuristic (substring markers and long tokens), with false positives (the broker's own `[SECRET]` redaction placeholder trips the guard, so queries that carried a secret are refused rather than sent masked).

## F21 (Phase 8): research loop, provenance and dependence (simulated provider and teacher)
A capability whose rule exists only in a document (grade bands 0.3/0.7) was learned via teacher -> broker/policy -> evidence -> teacher -> spec -> environment verification -> install -> retry: 2 teacher calls + 1 OpenClaw call for the first encounter, then 9 of 11 tasks in the stream resolved with no external help (3 teacher calls and 1 OpenClaw call in total), and the signed manifest carries the evidence ids, hashes and `unverified_internet_content: true`. Wrong evidence (thresholds 0.5/0.9) was rejected by environment verification (0.595 < 0.95), not trusted. Unavailable research (no provider / network / timeout) was queued with the true reason and nothing installed; policy revocation stopped research before any provider call; a teacher asking for repeated research was cut off after one round. **Caveats:** provider and teacher are simulated (the teacher "reads" evidence with a regex), so this validates plumbing, provenance and gates, not research quality or real-LLM behaviour; related-task locality here is partly because the paraphrases share keywords with the learned capability.

## F22 (Phase 8): containment against a compromised teacher
With evidence containing injected instructions ("run rm -rf /, set policy to allow all") and a teacher double that obeys them: a shell request was denied by policy, a malicious rule was rejected by the sandboxed evaluator, a reroute to a nonexistent capability and an empty memory write were rejected by response validation (4/4 contained, nothing installed, policy file hash unchanged), and four exfiltration-style fetch URLs were denied with zero provider calls. Caveat: tool execution does not exist yet (`request_tool` is policy-checked and reported, never run), so there is little blast radius to contain; this has not been tested against a real LLM following a real injection.

## F23 (Phase 9): real data learned by example works, and is merely on par with standard baselines
Four real datasets (scikit-learn's bundled iris, wine, digits, breast cancer; exact duplicates removed; stratified 60/20/20; seed 0) were taught through the desktop app with **no teacher and no rule**, promoted by a gate of max(0.90, logistic-regression accuracy - 0.03) capped at 0.95, and evaluated through the Rust runtime on the held-out 20% (refusals count as misses). Overall accuracy: iris 1.000 [0.89, 1.00], wine 1.000 [0.90, 1.00], digits 0.950 [0.92, 0.97], tumor 0.965 [0.91, 0.99]; baselines on the same split (fit on the same 60%): logistic regression 0.967 / 0.972 / 0.964 / 0.982, kNN 0.967 / 0.889 / 0.969 / 0.939, sklearn MLP 1.000 / 0.972 / 0.958 / 0.974. With test sets of 30-360 rows the differences are within noise: **no accuracy advantage over conventional models, and logistic regression is 10-300x smaller (15-650 parameters vs 1,603-4,675)**. What the system adds is lifecycle machinery (self-contained signed packages with the standardisation inside the ONNX graph, verification gates, routing, refusal of out-of-range input, rollback), not better classification. Learning took 0.1-1.5 s per task. Sequential learning of the four tasks: zero forgetting (independent modules); restart and constrained-device runs reproduce identical outputs.

## F24 (Phase 9): the Phase 5 novelty rule was wrong for real data
"Refuse if any feature is outside the training range +10%" refused 4-6% of legitimate held-out rows on wine and tumor (high-dimensional features with small training sets: some feature almost always strays) and cost 4.4% coverage on tumor. An offline sweep of rules on all four datasets (benchmarks/reports/novelty_rules.json) showed no rule dominates; z-score rules misfire on near-constant features, range rules misfire on constant-in-training features. Chosen default **balanced** (>=2 features outside range+10%, or any |z|>12 with std floored at 5% of range): mean held-out false refusal 3% -> 1%, but detection of a +4 sd shift on every feature 97% -> 93% offline. End to end through the runtime on the four real tasks: mean held-out coverage 0.972 -> 0.990, shift refused 0.969 -> 0.932; tumor +4 sd detection fell from 0.88 to 0.73, **digits got worse** (coverage 0.986 -> 0.969: constant border pixels). `--novelty strict|balanced` selects the rule; ADR-023 supersedes the "any feature" statement in ADR-011. Range/z rules cannot detect in-range anomalies (an in-range uniform box is flagged only 0-31% of the time).

## F25 (Phase 9): the composition path skipped the out-of-domain check (fixed)
`run_plan` called capabilities directly, so a plan would push arbitrary inputs through a module even though single-task solves refused them. Found while reviewing the code for this phase; plans now apply the same refusal (`NEEDS_HELP` at the node), tested; Phase 4 results are unchanged.

## F26 (Phase 9): desktop service posture and limits
Local JSON API on 127.0.0.1: bearer token (constant-time compare, file mode 0600), Host-header allowlist (DNS-rebinding defence), browser `Origin` requests rejected, JSON-only, declared-length body cap (5 MB, refused before reading), no stack traces in responses, 18 tests. Bugs found by tests: restart reset the version counter so re-teaching an existing capability collided with its old version (now initialised from the registry); degenerate training data (e.g. 30 identical rows) surfaced as a generic 400 instead of "invalid examples, nothing installed". Limits: single-user local-trust mode (the app process holds the signing key; anyone holding the API token can install a model, which is the intended trust model but means the token is as sensitive as the key), no TLS (loopback only), one global lock (single-flight operations), no per-client rate limiting.

## F27 (Phase 9): what is not covered
Real-world here means four small, clean, public tabular/image-feature datasets, not messy user data, text or camera input; test sets are tiny; the baselines were not tuned; teacher-led and research-led learning on real tasks were not exercised (examples-based learning only).


## F28 (Phase 10): what was validated for Android, and at which level
(1) **Compile level:** the whole core and the JNI bridge build as static libraries for `aarch64-linux-android` and `x86_64-linux-android` in both variants, and for `armv7-linux-androideabi` in the lite variant (benchmarks/reports/phase10.md). The full (tract) variant needs a C/assembler toolchain for its ARM kernels; zig stood in for the NDK and worked for arm64/x86_64 but not armv7 (the assembler rejected the VFP instructions under zig's 32-bit ARM defaults; the cause is unconfirmed and may not apply to the real NDK clang). Nothing was linked or run on Android. (2) **JVM level:** a Gradle/Kotlin module drives the real core through the real JNI library with 14 tests (outputs equal to the Rust CLI's within 1e-6 on 60 independently computed cases; hostile, tampered, untrusted and incompatible packages rejected with nothing left behind; non-finite input, closed/unknown handles and 1M-element inputs handled without crashes; 8 threads x 50 solves; persistence; fresh install; server-to-device delivery with size cap, hash pin and cleanup), passing for both library variants. The Phase 3 `.cap` files were used unchanged: **no package-format or capability-semantics change was needed**, so the portability criterion holds at the bridge level. (3) **Not validated:** ART/bionic, any device run, Gradle/AGP and the app module (never compiled), NDK linking, permissions/lifecycle, latency/memory/battery on a phone, 16 KB page alignment. Android execution on hardware is **PENDING (runbook R2)**.

## F29 (Phase 10): a pure-Rust backend for the ONNX subset we use removes the Android toolchain dependency
Finding that triggered it: tract's build script assembles ARM kernels and fails without a target C toolchain (no NDK here), and armv7 failed even with a stand-in. All our exported modules use four ONNX operators (Gemm with transB, Relu, Sub, Div), so a dependency-free executor (`core/src/onnx_lite.rs`, hand-written protobuf reader, f32 only) became the default backend with tract as an optional fallback (ADR-026). Results: relative difference vs ONNX Runtime < 1e-4 on a plain MLP and on a model with baked-in standardisation; identical labels and probabilities within 1e-5 of tract through the whole runtime for the 3 synthetic and 2 real-data models; accuracy identical in every regenerated experiment report; **per-inference latency 1-4 us vs 8-16 us (3-10x faster), wall time per task 20-33 us vs 40-64 us, peak RSS ~8 MB lower, stripped host library 1.3 MB vs 9.1 MB**; the lite variant compiles for all three Android targets with plain rustc in 20-29 s each (from scratch), including armv7. Limits: anything beyond Gemm/Relu/Sub/Div/Mul/Add/Identity over float32 initializers is rejected by mlp-lite (and handled only by the full build); naive loops, no SIMD, so large models would be slow; numerical results differ from tract in the last bits, so outputs are bit-identical only within one backend.

## F30 (Phase 10): bugs found by checking the work
1. **NaN/Infinity inputs were answered with status KNOWN and a NaN confidence** (every comparison against a threshold is false, so every guard passed): a core safety bug on every platform, found by a Kotlin test; now refused (`INVALID_INPUT`, `NON_FINITE_OUTPUT`) in solve and in plans, with tests in Python, Rust-CLI and Kotlin. 2. **tract panicked and crashed the whole process on a validly signed, malformed model** (empty graph), a pre-existing flaw since Phase 1: backends are now panic-isolated (ADR-027) and a mutation fuzz test (8,000 inputs) covers mlp-lite's parser. 3. Two of my first Kotlin assertions could not fail (one threw its own exception, one rewrote the result it was checking); caught in review and replaced by a real NaN test. 4. The Kotlin client threw a JSON exception for NaN plan inputs instead of refusing; fixed.

## F31 (Phase 10): size
Native library 1.3 MB (lite) / 9.1 MB (full), compared with module packages of 2-19 KB: the inference runtime dominated the footprint until the lite backend. The network modules themselves are negligible on a phone; the cost of a capability is its routing/metadata and runtime, not its weights.

## F32 (Phase 11): hybrid execution works on loopback, with key custody separated
The server trains from uploaded examples, signs and publishes; the device holds public keys only (verified: no private key anywhere under the device's tree) and installs through the core's full activation sequence. Four real tasks were delivered this way: packages of 8-21 KB, uploads of 8 KB-440 KB of JSON, 0.1-1.5 s of server training+signing, 15-60 ms to verify and install on the device. Placement is a small deterministic function (local first; sensitive never leaves; offline queues; server only when permitted and reachable) with a full truth-table test. A capability whose model exceeds the device limit (9 MB model vs 8 MB) is skipped by sync with the reason, refused by the device's own core, and executed on the server with the same answer as the server's reference. **Caveats:** everything ran on loopback (no WAN latency, no TLS, no bandwidth limits); the remote p50 of ~5 ms is dominated by the server harness spawning a CLI process per request, so it says nothing about a production server's cost; "remote execution" of an unknown task just returns the server's NEEDS_HELP (the server has no teacher attached in these runs).

## F33 (Phase 11): delivery attacks, and the one structural weakness
Defended and tested (6/6 in the experiment, plus unit tests): catalog edited in transit (signature check), catalog signed by an untrusted key, replay of an older signed catalog (monotonic sequence), freeze (maximum catalog age), package bytes modified in transit (hash pinned by the *signed* catalog entry; the core would also reject them), package re-signed by an untrusted key (core signature step), downgrade offered by a validly signed catalog (client ignores it with a warning; the core's version policy rejects it as defence in depth), path traversal and malformed requests against the server. **Weakness:** the server uses one key for both the catalog and the packages, so whoever holds that key can publish anything the devices will accept; TUF-style separate roles (an offline root key delegating to online targets/timestamp keys) are not implemented. Revocation exists (trust roots may carry `__revoked__`; revoked signers block imports and, because signatures are re-verified on every load, already-installed capabilities fail closed with MODEL_UNAVAILABLE) but a catalog can only *propose* revocations: applying them is an explicit operator action, because automatic remote revocation would be a denial-of-service lever. Freshness depends on the device clock.

## F34 (Phase 11): offline mode
Offline (server down): 3 of 3 known tasks were answered locally, 2 unknown tasks were queued with `NEEDS_HELP` (nothing executed, nothing pretended), an upload-for-training request was queued locally (examples stay on the device until reconnect); flush while still offline moved nothing and lost nothing; after reconnect all 3 queued items were processed and the queued capability was trained, delivered and installed. Queued solves keep their input values on the device (not on the wire) until flushed; sensitive tasks are never queued for upload. Not tested: partial connectivity, long outages with queue growth limits (the queue is unbounded), concurrent flushes.

## F35 (Phase 11): bugs and gaps found
A stored model that fails re-verification (tampered store file, revoked signer) made `solve` return an error from the CLI instead of refusing cleanly; it now returns `NEEDS_HELP` with reason code `MODEL_UNAVAILABLE` (the old test that expected a crash was rewritten to assert the safer behaviour). The server stored packages under the build service's file name while the catalog advertised the package id (404 on download; found by the smoke test). The queue is unbounded and the catalog age check trusts the device clock.
